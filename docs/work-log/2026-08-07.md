## 세션: JS → 네이티브 `launch()` 연결 (versionCode 15)

### 문제 상황

전날 세션에서:
- `InstalledAppsModule.kt`에 `launch()` 메서드 추가 완료
- JS `intentParser.ts`는 여전히 `Linking.openURL("intent:#Intent;package=xxx;end")` 사용 중

`intent:#Intent;package=xxx;end` 방식이 실패하는 이유:

```
Linking.openURL("intent:#Intent;package=com.google.android.youtube;end")
→ ActivityNotFoundException: No Activity found to handle Intent (no ACTION, no CATEGORY)
```

Android Intent URI 포맷에서 `#Intent;package=xxx;end`는 패키지 필터만 지정할 뿐 어떤 액티비티를 시작할지(ACTION_MAIN + CATEGORY_LAUNCHER)를 명시하지 않는다. Android는 시작할 액티비티를 찾지 못하고 예외를 던진다.

반면 `pm.getLaunchIntentForPackage(packageName)`는 해당 패키지의 런처 엔트리 포인트를 OS가 직접 조회해 반환한다. 이것이 Google Assistant, Samsung Bixby, GiGA Genie 등 모든 음성 어시스턴트가 사용하는 표준 방법이다.

### 변경 내용

**`src/features/intent/intentParser.ts`**

`openAppByName` 함수 내 2순위·3순위 앱 실행 경로에서 `Linking.openURL` 제거, `InstalledApps.launch()` 대체:

```typescript
// 변경 전 (2순위)
await Linking.openURL(`intent:#Intent;package=${packageName};end`);

// 변경 후 (2순위)
await InstalledApps.launch(packageName);
```

```typescript
// 변경 전 (3순위 단일 매칭)
await Linking.openURL(`intent:#Intent;package=${matches[0].packageName};end`);

// 변경 후 (3순위 단일 매칭)
await InstalledApps.launch(matches[0].packageName);
```

1순위(커스텀 URI 스킴: `vnd.youtube:`, `kakaomap://` 등)는 유지.
이유: 유튜브, 카카오맵 등은 커스텀 스킴으로 직접 특정 화면 진입이 가능하므로 그대로 활용.

**`android/app/build.gradle`**

```groovy
versionCode 14 → 15
```

### 기술적 포인트

**왜 `intent:#Intent;...;end` 방식은 작동하지 않나:**

이 URI 포맷은 `adb shell am start -a ... -n ...` 과 같은 full intent를 URI 인코딩한 것이다. `package` 필터만 있고 `ACTION_MAIN`/`CATEGORY_LAUNCHER`가 없으면 Android는 어떤 액티비티를 시작해야 할지 알 수 없다. `getLaunchIntentForPackage`는 OS가 이 정보를 자동으로 채워주기 때문에 항상 성공한다(앱이 설치되어 있다면).

**1순위 커스텀 URI 스킴은 유지하는 이유:**

유튜브의 `vnd.youtube:video_id=xxx` 나 카카오맵의 `kakaomap://search?q=xxx` 같이 딥링크로 특정 기능에 직접 진입할 수 있는 경우, 단순히 앱을 여는 것보다 사용자 경험이 낫다. 향후 "유튜브에서 XXX 검색해줘" 같은 명령어를 지원할 때 이 경로를 활용할 수 있다.

## 세션: Android 11+ 패키지 가시성 버그 (versionCode 16)

### 증상

versionCode 15 설치 후 유튜브·인스타 외에 모든 앱이 "찾을 수 없어요" 반환.

### 원인

`AndroidManifest.xml`의 `<queries>` 블록에 런처 앱 조회 권한이 없었다.

Android 11(API 30)+에서 앱이 다른 앱의 정보를 조회하려면 `<queries>` 에 명시적으로 선언해야 한다. 기존 선언:
```xml
<queries>
  <package android:name="com.google.android.googlequicksearchbox"/>
  <intent><action android:name="android.speech.RecognitionService"/></intent>
</queries>
```
음성인식 앱만 보이고 나머지는 전혀 안 보임. `InstalledApps.getAll()`이 빈 배열 반환 → 매칭 불가 → not_found.

유튜브·인스타가 됐던 이유: `parseIntent`가 package_name을 반환하고, `apps.some()` 체크 없이 `launch()` 직접 호출했기 때문 (이건 우연히 맞은 것).

### 수정

```xml
<queries>
  <intent>
    <action android:name="android.intent.action.MAIN"/>
    <category android:name="android.intent.category.LAUNCHER"/>
  </intent>
</queries>
```

이 한 블록으로 기기에 설치된 모든 런처 앱이 보이게 됨. `queryIntentActivities()`와 `getLaunchIntentForPackage()` 모두 정상 동작.

## 세션: 앱 매칭 구조 개선 3단계 (versionCode 17→20)

### 1단계: Gemini NLU 매칭 도입 (v17) — 부분 성공

**문제:** 신한은행 → "신한 SOL뱅크", 제미나이 → "Gemini" 처럼 레이블이 달라서 로컬 퍼지 매칭 실패.

**시도:** `geminiMatchApp()` 함수 추가 — 설치 앱 목록 전체를 Gemini에 보내 NLU로 매칭.

```
사용자: "신한은행"
앱 목록: 신한 SOL뱅크|com.shinhan.sbanking, ...
→ Gemini: {"matches":["com.shinhan.sbanking"]}
```

**결과:** 구조는 맞지만 두 번째 Gemini 호출이 생겨서 503(과부하) 발생 시 전부 실패.

### 2단계: 중간 수정 (v18~19) — apps.some() 체크 제거

**발견:** `parseIntent`가 이미 `package_name: "com.shinhan.sbanking"` 을 반환하는데, `openAppByName`에서 `apps.some(a => a.packageName === packageName)` 체크에서 탈락(앱 목록에 없음) → 불필요하게 `geminiMatchApp` 호출 → 503.

**수정:** `apps.some()` 제거. 패키지명 있으면 그냥 `launch()` 시도.

```typescript
// 변경 전
if (packageName && apps.some((a) => a.packageName === packageName)) {
// 변경 후
if (packageName) {
```

### 3단계: 구조 단순화 (v20) — geminiMatchApp 완전 제거

**발견:** 두 번째 Gemini 호출 자체가 설계 실수. `parseIntent`가 이미 Gemini를 1회 호출하고, 거기서 package_name을 반환한다. 두 번 호출할 이유가 없다.

**최종 구조:**
```
parseIntent(발화) → Gemini 1회 → {intent:"open_app", package_name:"com.shinhan.sbanking"}
→ InstalledApps.launch("com.shinhan.sbanking") ← 끝
```

package_name이 비었을 때(진짜 모호한 경우: "KB 켜줘")만 로컬 레이블 매칭 → picker 표시.

**`parseIntent` 프롬프트 강화:**
- "아는 앱이면 반드시 package_name 반환" 명시
- 신한은행, 하나은행, 우리은행, 제미나이, 지피티, 당근마켓 예시 추가
- 결과: 쿠팡이츠처럼 예시에 없는 앱도 Gemini 학습 데이터로 자동 처리

**`geminiMatchApp` 함수 완전 제거** → API 호출 경로가 항상 1회로 고정.

### 기술적 교훈

**"Gemini를 두 번 부르지 마라"**

첫 번째 Gemini 호출(`parseIntent`)이 앱 이름뿐 아니라 package_name까지 반환할 수 있다. Gemini는 수만 개 Android 앱의 패키지명을 학습 데이터에 가지고 있다. 이걸 활용하면 두 번째 호출은 필요 없다. 두 번째 호출을 만드는 순간 503 위험이 2배가 되고, 비용도 2배가 된다.

## 세션: SpeechRecognizer 두 번째 녹음 버그 (versionCode 20 포함)

### 증상

첫 번째 녹음은 정상. 두 번째 녹음 시 `UNKNOWN_ERROR` 또는 `CLIENT_ERROR` 반환.

### 원인

`SpeechRecognitionModule.kt`의 `startListening()`에서:

```kotlin
recognizer?.destroy()
recognizer = SpeechRecognizer.createSpeechRecognizer(reactContext)
```

`destroy()` 전에 `cancel()`을 호출하지 않아 마이크가 즉시 해제되지 않음. Android SpeechRecognizer는 진행 중인 인식을 먼저 중단(`cancel`)해야 `destroy()`가 마이크를 완전히 반납한다.

### 수정

```kotlin
recognizer?.cancel()   // 진행 중인 인식 중단
recognizer?.destroy()  // 리소스 해제
recognizer = null      // 참조 제거
recognizer = SpeechRecognizer.createSpeechRecognizer(reactContext)
```

`null` 대입은 GC가 이전 객체를 즉시 수집하도록 명시적으로 끊어주는 방어 코드다.

## 세션: SilverLink 기능 연동 — TTS·Safety Severity·대화 로그 (versionCode 22)

### 포팅 기준

SilverLink(`silverlink-web-input`)에서 백엔드 없이 모바일 단독으로 동작 가능한 것만 추렸다.
- 제외: RAG 시스템, 알림 큐, Supabase 의존 기능, 통화 자동 분석
- 채택: (1) TTS, (2) 안전 알림 severity, (3) 대화 로그

### 1. TTS — `src/features/tts/TtsService.ts` (신규)

`expo-speech` 패키지 설치 후 얇은 래퍼 생성.

- 언어: `ko-KR`, 속도: `0.85` (어르신 친화적 — 기본값보다 느림)
- `speak()` 호출 시 직전 발화를 `stop()` 후 재시작 (중복 재생 방지)
- 읽히는 시점:
  - `general_answer` → 답변 자동 읽기 (최대 200자) + "다시 읽기" 버튼
  - `result` 전화 완료 → "○○님 전화 화면을 열었어요" 읽기
  - `safety_concern` 감지 → severity 따라 다른 문장 읽기
  - 약 알림 설정 완료 → 확인 메시지 읽기
- 화면 이탈(`handleReset`) 또는 컴포넌트 언마운트 시 `ttsStop()` 호출

### 2. 안전 알림 Severity — `src/features/intent/intentParser.ts` 수정

SilverLink `safety-alert-analyzer.ts`의 카테고리→심각도 분류를 정적 매핑으로 이식.

```typescript
const CATEGORY_SEVERITY: Record<SafetyCategory, SafetySeverity> = {
  fall_risk:            "high",
  urgent_medical:       "high",
  medication_concern:   "medium",
  mobility_concern:     "medium",
  mental_health_concern:"medium",
  nutrition_concern:    "low",
  social_isolation:     "low",
};
```

추가 API 호출 없이 `parseIntent` 반환값에 `severity` 필드 추가.
UI에서 색상 구분: high=빨강 테두리+뱃지, medium=노랑, low=초록.

### 3. 대화 로그 — `src/features/conversation-log/ConversationLogService.ts` (신규)

AsyncStorage 기반 로컬 로그. 대화 완료 이벤트마다 `addLog(emoji, summary)` 호출.
IDLE 화면에 "오늘 한 일" 섹션으로 최근 3건 표시.

로그 발생 시점: 앱 실행 완료, 전화 완료, 업체 전화 완료, 일반 질문 완료, 약 알림 설정.

### 기술적 교훈

**"TTS는 어르신 UX의 안전망이다"**

어르신은 글씨가 작거나 화면이 낯설면 내용을 읽지 않는다. TTS가 없으면 AI 답변은 어르신에게 도달하지 않는다. `speak()` 한 줄이 이 앱의 해자(어르신 친화성)를 실제로 실현하는 것이다. SilverLink가 통화 분석 후 가족에게 정보를 전달하듯, ai-myeoneuri는 TTS로 어르신에게 직접 전달한다.

## 세션: 어르신 특화 AI 응답 튜닝 (versionCode 23)

### 목표

"일반 챗봇과 차별화되는 어르신 답변"을 만드는 것이 이 앱의 해자다.
Gemini는 기본적으로 긴 글, 마크다운, 영어 혼용, 불릿 목록으로 답한다.
어르신은 이걸 읽지 않는다. 교정이 필요하다.

### 변경 1: `ELDERLY_SYSTEM_PROMPT` 전면 재작성 (`intentParser.ts`)

**기존 프롬프트 문제점:**
- 규칙만 있고 예시가 없음 → Gemini가 규칙을 해석하는 방식이 불안정
- "짧게 써"라고 했지만 "최대 N문장"이 없음 → 여전히 길게 나올 수 있음
- TTS 관점이 없음 → 기호(`%`, `°C`, `→`)가 읽혔을 때 어색함

**새 프롬프트 구조:**
1. 페르소나: "AI 며느리" — 친절하지만 어르신을 어린아이 취급 안 함
2. 절대 규칙 5개 (위반 = 답변 전체 실패로 정의):
   - 최대 4문장
   - 글머리 기호·마크다운 금지
   - 영어 금지
   - 의료 진단 금지
   - 핵심 첫 문장
3. Few-shot 예시 3쌍 (나쁜 예 → 좋은 예):
   - 혈압 수치: 영어 약어(`mmHg`, `Stage`) 제거
   - 날씨: `°C` 제거, 핵심 행동 제안 추가
   - 복약법: 불릿 목록 → 흘러가는 문장

**temperature 조정:** 0.7 → 0.4
어르신 답변은 창의성보다 일관성이 중요하다. 같은 질문에 매번 같은 수준의 답이 나와야 신뢰 가능.

**maxOutputTokens 추가:** 512
토큰 상한을 걸지 않으면 Gemini가 지시를 무시하고 길게 쓰는 경우가 있다.

### 변경 2: `prepareForSpeech()` 추가 (`TtsService.ts`)

TTS로 읽히기 전 기호를 한국어 말로 변환:

```
% → 퍼센트
℃/°C → 도  
→ → 에서
· → (공백)
$ → 달러
₩ → 원
/ → 또는
\n → . (문장 구분)
```

문장 4개 초과 시 잘라낸다. `speak()`가 내부에서 `prepareForSpeech()`를 자동 호출하므로 호출부에서 별도 처리 불필요.

**rate 조정:** 0.85 → 0.82
어르신 청력은 개인차가 크다. 약간 더 느리게 해서 안전 마진을 확보.

### 검증 불가 항목

실기기 없이 다음을 검증할 수 없다:
- 실제 어르신이 TTS 속도를 편안하게 느끼는지 (Task 4 가족 테스트에서 확인)
- 시스템 프롬프트 강화가 Gemini 응답 품질을 실제로 올렸는지 (Task 4에서 테스트 항목)

### 기술적 교훈

**"시스템 프롬프트는 규칙이 아니라 예시로 가르쳐야 한다"**

규칙("짧게 써")만 있으면 Gemini는 자기 해석대로 실행한다.
예시("나쁜 예 → 좋은 예")를 붙이면 Gemini가 원하는 출력 패턴을 실제로 확인하고 따라한다.
시스템 프롬프트에서 few-shot 예시 3쌍은 규칙 6개보다 훨씬 효과적이다.
