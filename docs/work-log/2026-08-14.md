# 2026-08-14 개발일지

## 오늘의 요약

오늘은 AI 며느리 앱의 B 카드 시퀀스 중 B-7 "가르치는 루프"를 구현했다. 기존에 음성 인식이 실패하면 "다시 말씀해 주세요"라는 Alert만 반복되던 구조를, 실패 시 확인 질문 화면으로 전환해 사용자가 직접 의도를 선택하면 그 결과를 L1 캐시에 저장하는 방식으로 개선했다. 이로써 같은 발화가 다시 들어왔을 때 Gemini API 호출 없이 즉시 처리되는 자기교정 루프가 완성됐다.

연속 3회 "다시 말씀해 주세요"가 나오는 경로를 코드 수준에서 차단한 것이 핵심이다. 이전 구조에서는 `intent === "unknown"`이 별도 처리 없이 일반 연락처 검색 폴백으로 빠졌고, 검색 실패 시 Alert가 계속 반복될 수 있었다.

## 세션: B-7 가르치는 루프

### 요청과 목표

- B-7 스펙: 인식 실패(unknown intent) 시 "다시 말씀해 주세요" 반복 대신 확인 질문 화면 표시
- 사용자 선택 → L1 캐시 저장 → 다음 동일 발화 시 L1에서 즉시 해결
- 수용 기준: "다시 말씀해 주세요"가 연속 3회 나오는 경로가 코드상 존재하지 않음

### 구현 및 변경 내용

**새 함수:** `correctL1Cache(utterance, intent)` in `intentL1Cache.ts`
- `saveToL1Cache`와 동일한 로직이지만 `unknown` 체크 없음
- 사용자가 직접 선택한 인텐트이므로 unknown이 아닌 경우만 호출됨

**ScreenState에 신규 타입 추가:** `{ type: "unknown_confirm"; utterance: string }`

**handleSearch 수정:** `parsed.intent === "unknown"` 케이스를 fallthrough 전에 명시 처리
- 기존: unknown → searchContacts 폴백 → no_results Alert "다시 말씀해 주세요"
- 변경: unknown → `unknown_confirm` 스크린 전환

**신규 핸들러 2개:**
- `handleUnknownCallIntent(utterance)`: 전화 선택 → `correctL1Cache` + `searchContacts` 직접 실행
- `handleUnknownSearchIntent(utterance)`: 검색 선택 → `correctL1Cache` + `searchBusinesses` 직접 실행

**unknown_confirm 스크린 JSX:**
- "잘 못 들었어요 / [발화 원문] / 어떻게 도와드릴까요?"
- 전화할게요 / 주변 검색할게요 / 닫기 버튼
- 즐겨찾기가 있으면 즐겨찾기 바로가기 표시

### 문제와 해결 과정

**공백 정규화 테스트 가정 오류:**
- `normalizeKey("  지은  한테  전화  ")` 결과가 `"지은한테전화"`라고 가정했으나 실제는 `"지은 한테 전화"` (공백 압축, 제거 아님)
- 테스트 lookup 키를 `"지은 한테 전화"`로 수정

### 기술적 의사결정

**왜 handleSearch 재귀호출 대신 직접 처리를 선택했나?**

초기에 "전화할게요" 버튼을 누르면 `correctL1Cache` 저장 후 `handleSearch(utterance)` 재호출을 고려했다. 이 경우 L1 캐시에서 읽혀 `call_contact` intent로 처리되는 것이 맞다. 하지만 문제가 있다: `call_contact`의 `contactName`이 발화 전체(`"지은이한테 전화해"`)가 되어버린다. `searchContacts("지은이한테 전화해")` 로는 "지은이"를 찾지 못할 수 있다.

결론: 핸들러 내부에서 `searchContacts(utterance)` 직접 호출. 발화 원문으로 검색하고, 결과가 없으면 즐겨찾기 안내로 대체한다.

**correctL1Cache의 의미:**
- `saveToL1Cache`와 코드가 거의 동일하지만 분리한 이유: 호출 의미론이 다르다
- `saveToL1Cache`: Gemini 분류 결과를 저장 (자동)
- `correctL1Cache`: 사용자가 능동적으로 정정한 결과를 저장 (의도적 교정)
- 나중에 정정 횟수 추적, 신뢰도 가중치 등 확장 시 분리해둔 것이 유리하다

## 세션: B-8 조용한 이상 감지

### 요청과 목표

- B-8 스펙: 어르신 폰 사용 패턴을 온디바이스에서 14일 학습 → 오늘 패턴이 이탈 시 가족에게 알림
- 핵심 제약: 원본 로그를 서버로 보내지 않음, 단말 내 학습·판단만 허용
- `PACKAGE_USAGE_STATS` 권한 사용 (ProtectedPermission)

### 구현 내용

**Android 네이티브 모듈 (Kotlin):**
- `UsageStatsModule.kt`: `hasPermission()`, `requestPermission()`, `getDailyUsage()`
  - `AppOpsManager.checkOpNoThrow`로 권한 확인 (일반 런타임 다이얼로그 없음)
  - `requestPermission()` → `Settings.ACTION_USAGE_ACCESS_SETTINGS` Intent 실행
  - `getDailyUsage()` → 자정부터 현재까지 ACTIVITY_RESUMED/PAUSED 이벤트 집계
- `UsageStatsPackage.kt`: ReactPackage 구현체
- `AndroidManifest.xml`: `PACKAGE_USAGE_STATS` 권한 추가 (`tools:ignore="ProtectedPermissions"`)
- `MainApplication.kt`: `add(UsageStatsPackage())` 등록

**JS 레이어:**
- `UsageStatsAdapter.ts`: `hasUsagePermission()`, `requestUsagePermission()`, `getDailyUsage()`  
  (Android 전용. iOS에서는 항상 null/false 반환)
- `BaselineService.ts`: 14일 기준선 학습 + 이상 감지
  - `DailyUsageSample`: `{ date, firstUsageHour, totalForegroundMin }`
  - `recordDailyUsage()`: AsyncStorage에 최대 90일 보관
  - `detectAnomaly()`: firstUsageHour +3h → mild, 미사용+4h 경과 → significant; 사용시간 평균 30% 미만 → mild
  - `markAnomalyDismissed()` / `isAnomalyDismissed()`: 하루 1회만 알림
  - `isAnomalyDetectionEnabled()` / `setAnomalyDetectionEnabled()`: 기능 토글

**index.tsx 변경:**
- B-8 관련 import 추가 (BaselineService, UsageStatsAdapter)
- `anomalyEnabled`, `hasAnomalyPermission` state 추가
- `checkAnomalyOnce()`: 앱 시작 시 1회 실행, 이상 감지 시 TTS + significant면 SilverLink 리포트
- 설정 모달에 토글 행 추가: Switch(on/off) + 권한 미허용 시 "사용 통계 권한 허용" 버튼

### 막혔던 지점

**SafetyCategory / SafetySeverity 타입 불일치:**
- `reportSafetyConcernToSilverLink("daily_pattern", "moderate", ...)` 작성 → tsc 에러
- `SafetyCategory`에는 `"daily_pattern"`이 없음; 행동 이상은 `"social_isolation"`이 가장 가깝다
- `SafetySeverity`는 `"low" | "medium" | "high"` → `"moderate"` 아님. `"medium"`으로 수정
- **교훈:** 기존 타입 유니온을 구현 전에 확인하지 않고 의미적으로 추측해 썼다가 두 번 수정

**PACKAGE_USAGE_STATS는 일반 권한 다이얼로그로 허용 불가:**
- `ActivityCompat.requestPermissions()`로 요청해도 시스템이 거절
- `AppOpsManager.OPSTR_GET_USAGE_STATS`로 상태 확인 후 설정 앱으로 유도해야 함
- React Native에서 이 패턴을 쓰는 npm 패키지가 없어 직접 Kotlin 모듈 작성

### 기술적 판단

**왜 npm 패키지 대신 직접 구현?**
`react-native-device-info`가 foregroundTime을 제공하지만 정밀도·이벤트 단위 접근이 안 됨.
`UsageEvents.Event.ACTIVITY_RESUMED/PAUSED` 수준의 세밀한 집계가 필요하므로 직접 작성.

**왜 B-4와 같은 릴리즈에 넣지 않는가?**
Play Store 심사 시 민감 권한이 여러 개 추가되면 거절 원인을 특정할 수 없다.
`PACKAGE_USAGE_STATS`와 `BIND_SCREENING_SERVICE`를 함께 추가하면 리뷰어 입장에서
어떤 게 문제인지 알 수 없다. 권한별 독립 릴리즈가 Play 심사 통과율을 높인다.
