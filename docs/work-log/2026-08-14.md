# 2026-08-14 개발일지

## 오늘의 요약

오늘은 AI 며느리 앱의 B 카드 시퀀스 중 B-7 "가르치는 루프"를 구현했다. 기존에 음성 인식이 실패하면 "다시 말씀해 주세요"라는 Alert만 반복되던 구조를, 실패 시 확인 질문 화면으로 전환해 사용자가 직접 의도를 선택하면 그 결과를 L1 캐시에 저장하는 방식으로 개선했다. 이로써 같은 발화가 다시 들어왔을 때 Gemini API 호출 없이 즉시 처리되는 자기교정 루프가 완성됐다.

연속 3회 "다시 말씀해 주세요"가 나오는 경로를 코드 수준에서 차단한 것이 핵심이다. 이전 구조에서는 `intent === "unknown"`이 별도 처리 없이 일반 연락처 검색 폴백으로 빠졌고, 검색 실패 시 Alert가 계속 반복될 수 있었다.

## 세션: B-7 가르치는 루프

### 요청과 목표

- B-7 스펙: 인식 실패(unknown intent) 시 "다시 말씀해 주세요" 반복 대신 확인 질문 화면 표시
- 사용자 선택 → L1 캐시 저장 → 다음 동일 발화 시 L1에서 즉시 해결
- 수용 기준: "다시 말씀해 주세요"가 연속 3회 나오는 경로가 코드상 존재하지 않음

### 구현 및 변경 내용

**새 함수:** `correctL1Cache(utterance, intent)` in `intentL1Cache.ts`
- `saveToL1Cache`와 동일한 로직이지만 `unknown` 체크 없음
- 사용자가 직접 선택한 인텐트이므로 unknown이 아닌 경우만 호출됨

**ScreenState에 신규 타입 추가:** `{ type: "unknown_confirm"; utterance: string }`

**handleSearch 수정:** `parsed.intent === "unknown"` 케이스를 fallthrough 전에 명시 처리
- 기존: unknown → searchContacts 폴백 → no_results Alert "다시 말씀해 주세요"
- 변경: unknown → `unknown_confirm` 스크린 전환

**신규 핸들러 2개:**
- `handleUnknownCallIntent(utterance)`: 전화 선택 → `correctL1Cache` + `searchContacts` 직접 실행
- `handleUnknownSearchIntent(utterance)`: 검색 선택 → `correctL1Cache` + `searchBusinesses` 직접 실행

**unknown_confirm 스크린 JSX:**
- "잘 못 들었어요 / [발화 원문] / 어떻게 도와드릴까요?"
- 전화할게요 / 주변 검색할게요 / 닫기 버튼
- 즐겨찾기가 있으면 즐겨찾기 바로가기 표시

### 문제와 해결 과정

**공백 정규화 테스트 가정 오류:**
- `normalizeKey("  지은  한테  전화  ")` 결과가 `"지은한테전화"`라고 가정했으나 실제는 `"지은 한테 전화"` (공백 압축, 제거 아님)
- 테스트 lookup 키를 `"지은 한테 전화"`로 수정

### 기술적 의사결정

**왜 handleSearch 재귀호출 대신 직접 처리를 선택했나?**

초기에 "전화할게요" 버튼을 누르면 `correctL1Cache` 저장 후 `handleSearch(utterance)` 재호출을 고려했다. 이 경우 L1 캐시에서 읽혀 `call_contact` intent로 처리되는 것이 맞다. 하지만 문제가 있다: `call_contact`의 `contactName`이 발화 전체(`"지은이한테 전화해"`)가 되어버린다. `searchContacts("지은이한테 전화해")` 로는 "지은이"를 찾지 못할 수 있다.

결론: 핸들러 내부에서 `searchContacts(utterance)` 직접 호출. 발화 원문으로 검색하고, 결과가 없으면 즐겨찾기 안내로 대체한다.

**correctL1Cache의 의미:**
- `saveToL1Cache`와 코드가 거의 동일하지만 분리한 이유: 호출 의미론이 다르다
- `saveToL1Cache`: Gemini 분류 결과를 저장 (자동)
- `correctL1Cache`: 사용자가 능동적으로 정정한 결과를 저장 (의도적 교정)
- 나중에 정정 횟수 추적, 신뢰도 가중치 등 확장 시 분리해둔 것이 유리하다

## 세션: F2-2 온디바이스 스미싱 방어 — SMS 수신 + 경고 카드

### 요청과 목표

- PRD-B2C-1000subs.md F2-2: 수신 SMS를 온디바이스에서 분류, 위험 시 경고 카드
- 원문 서버 미전송 (ADR-008 유지), RECEIVE_SMS (제한 권한 아님)
- 수용 기준: 재현율 ≥ 0.85, 오탐률 ≤ 0.10, 분류 지연 ≤ 300ms

### 발견: 룰 엔진은 이미 존재

`src/features/safety/smishingRules.ts`와 `tests/smishingRules.test.ts` 100건 테스트셋이
이미 구현되어 있었고 전체 통과 상태였다. 이번 세션에서는 네이티브 수신 레이어만 추가했다.

### 구현 내용

**Android 네이티브 모듈 (Kotlin):**
- `SmsListenerModule.kt`: BroadcastReceiver 등록/해제 + RCTDeviceEventEmitter로 `SmsReceived` 이벤트 발행
  - `addListener/removeListeners` stub: NativeEventEmitter 연결에 필요
  - `invalidate()` 오버라이드: 모듈 언마운트 시 BroadcastReceiver 자동 해제
  - Android 13+ (TIRAMISU): `RECEIVER_EXPORTED` 플래그 필수
- `SmsListenerPackage.kt`: ReactPackage 구현체
- `AndroidManifest.xml`: RECEIVE_SMS 권한 + receiver 선언 (priority=999)
- `MainApplication.kt`: `add(SmsListenerPackage())` 등록

**JS 레이어:**
- `src/features/safety/SmsReceiverAdapter.ts`: `startSmsListening()`, `stopSmsListening()`, `addSmsListener(handler)` — Android 전용, iOS 투명 fallback
- `index.tsx`: useEffect에서 리스너 시작 → SmsReceived 이벤트 → `detectSmishing()` 실행
  - risk high/medium → `smishing_alert` 화면 전환 + TTS "위험한 문자가 왔어요"
  - cleanup 시 `stopSmsListening()` + `removeSmsListener()` 호출
- `ScreenState`에 `smishing_alert` 타입 추가
- JSX: 위험도별 경고 카드 (high = 빨간 테두리 "위험한 문자예요!", medium = "수상한 문자예요")
- 스타일: `smishingIcon`, `smishingTitle`, `smishingSender`, `smishingBody`, `smishingAdvice`

### 기술적 판단

**왜 READ_SMS가 아닌 RECEIVE_SMS인가?**
`READ_SMS`는 Play Store 제한 권한(restricted) — 승인 서류 필요.
`RECEIVE_SMS`는 일반 위험 권한(dangerous) — 런타임 다이얼로그로 허용 가능.
수신 SMS를 분류하는 데 기존 받은 문자함을 읽을 필요가 없다.

**왜 차단하지 않고 경고만 하는가?**
"잘못 차단하면 진짜 급한 연락을 놓친다" — F2 설계 원칙 1조.
어르신이 중요한 통화/문자를 놓치면 제품 신뢰가 무너진다.

**RECEIVER_EXPORTED 분기가 필요한 이유:**
Android 13부터 BroadcastReceiver 등록 시 EXPORTED 또는 NOT_EXPORTED 플래그를 명시하지 않으면 예외 발생.
시스템 SMS broadcast를 받으려면 EXPORTED가 필요하다.
