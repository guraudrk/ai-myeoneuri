# 2026-08-06 개발일지

## 오늘의 요약

흰 화면에서 벗어나지 못하는 버그를 진단·해결하고, 실기기 테스트에서 발견된 앱 실행 관련 버그 5개를 분석했다.

흰 화면 문제는 Android 빌드 설정의 `debuggableVariants` 기본값이 원인이었다. React Native Gradle 플러그인은 기본적으로 debug 빌드에서 JS 번들 생성을 건너뛰는데, 개발 중에는 Metro가 번들을 실시간으로 공급해줘서 문제가 없었다. 그런데 `./gradlew assembleDebug`로 직접 APK를 빌드해 실기기에 설치하면 Metro 없이 앱이 실행되고, JS 번들이 없으니 React가 아예 마운트되지 않고, `SplashScreen.preventAutoHideAsync()`가 걸려 있어 스플래시 화면이 영원히 유지됐다. `debuggableVariants = []`로 설정하자 debug APK에도 번들이 포함되어 정상 작동했다.

이 과정에서 versionCode 12~13까지 세 단계 진단을 거쳤다. ErrorBoundary + globalError 핸들러 → JS 자체가 로드되지 않음 확인 → expo-router 완전 우회 `AppRegistry.registerComponent` → 여전히 흰 화면 → 빌드 산출물(APK) 분석으로 번들 자체가 없음을 확인하는 흐름이었다.

앱 실행 관련 버그는 이날 수정하지 않고 다음 세션에서 PackageManager 방식으로 전면 교체하기로 결정했다.

## 세션: 흰 화면 버그 진단 및 수정 (versionCode 11~14)

### 증상

versionCode 10 이후 앱이 초기 로딩 화면에서 벗어나지 못함. 어떤 화면도 렌더링되지 않음.

### 진단 과정

**versionCode 11 — Stack.Screen 제거 (실패)**
- 이전 세션에서 `app/index.tsx`에 `<Stack.Screen>` 추가 시점과 증상 발생 시점이 겹침
- `<Stack.Screen>`과 `Stack` import 제거, `headerShown: false`를 `_layout.tsx`로 이동
- 결과: 여전히 흰 화면. 원인이 아님.

**versionCode 12 — ErrorBoundary + SplashScreen.hideAsync 강제 (실패)**
- `_layout.tsx`에 3중 안전망 추가:
  - 모듈 레벨 `SplashScreen.preventAutoHideAsync()`
  - `globalThis.ErrorUtils.setGlobalHandler` 로 미잡힌 JS 에러 캡처
  - `ErrorBoundary` 클래스 컴포넌트 — `componentDidMount`에서 `SplashScreen.hideAsync()`
  - `useEffect(() => { SplashScreen.hideAsync() }, [])` — 렌더 직후 강제 숨김
- 에러가 있으면 빨간 화면에 에러 메시지 표시
- 결과: 여전히 흰 화면. **React 자체가 마운트되지 않음 확인.** JS 로드 실패.

*참고: `global`은 TypeScript에서 `Cannot find name 'global'` 에러 발생. `globalThis`로 수정.*

**versionCode 13 — expo-router 완전 우회 (실패 → 핵심 단서 확보)**
- `index.js` 신규 생성: expo-router 미사용, `AppRegistry.registerComponent`로 직접 파란 진단 화면 등록
- `package.json "main"` → `"index.js"` (expo-router/entry에서 변경)
- 결과: 여전히 흰 화면. **expo-router 문제가 아님 확인. JS 번들 자체가 실행되지 않음.**

**APK 직접 분석 — 원인 확인**
```
APK assets/ 목록:
  assets/app.config  [0.6 KB]   ← 있음
  (index.android.bundle 없음)   ← 번들 자체가 없음!
```

JS 번들이 APK에 포함되지 않은 것이 원인.

### 근본 원인

React Native Gradle 플러그인의 `debuggableVariants` 기본값:

```groovy
// build.gradle 기본값 (주석 처리된 상태)
// debuggableVariants = ["liteDebug", "prodDebug"]
// → 기본값: ["debug"]
```

기본값 `["debug"]`는 **debug 빌드에서 JS 번들링 task를 건너뜀**. `expo run:android`로 빌드하면 Metro가 자동으로 실행돼 번들을 실시간 공급하므로 문제가 없다. 하지만 `./gradlew assembleDebug`로 빌드하면 APK에 번들이 없고, Metro 없이 설치하면 JS가 로드되지 않는다.

왜 versionCode 9까지는 됐나: 초기에 `expo run:android`로 빌드하거나 Metro가 실행 중인 환경에서 테스트했기 때문.

### 수정

`build.gradle`에 한 줄 추가:

```groovy
debuggableVariants = []  // 빈 배열 = debug 빌드에도 번들 포함
```

`package.json "main"` 복원:
```json
"main": "expo-router/entry"
```

`index.js` 삭제 (진단용 파일).

### 검증

```
versionCode 14 clean build: 305 tasks executed (이전 versionCode 13: 21 tasks)
```

번들 task가 추가로 실행됐음을 확인. APK 재분석:
```
assets/app.config  [0.6 KB]
assets/index.android.bundle  [1718.2 KB]  ← 번들 생성 확인
```

사용자 실기기 테스트: "실행 복구됨" 확인.

### 변경 파일

- `android/app/build.gradle`: `debuggableVariants = []` 추가, versionCode 13 → 14
- `package.json`: `"main"` → `"expo-router/entry"` 복원
- `index.js`: 삭제 (진단용)
- `app/_layout.tsx`: 진단 코드(ErrorBoundary, globalError 핸들러) 아직 남아있음 — 다음 세션 초에 제거 예정

### 기술적 의사결정

**왜 release 빌드가 아니라 debuggableVariants = []로 해결했나:**
- release 빌드: 번들 포함되지만 매번 릴리즈 빌드를 올리는 건 개발 속도 저하
- `debuggableVariants = []`: debug 빌드에도 번들 포함, Metro 없이 어느 환경에서나 설치 가능
- 단점: debug 빌드 시간이 다소 늘어남 (21 tasks → 305 tasks). 받아들일 수 있는 트레이드오프.

## 세션: 실기기 테스트 버그 분석 (수정 미완료 — 다음 세션 예정)

### 발견된 버그 5개

실기기(Galaxy A34) 테스트에서 발견된 앱 실행 관련 버그.

**버그 1. KB은행 켜줘 → 선택창 없이 바로 열림**
- 원인: Gemini가 "KB은행"을 `package_name: "com.kbstar.kbbank"` 로 반환 → `openAppByName` 1순위(packageName)에서 KB국민은행이 바로 열림. APP_FAMILIES 선택창 표시 로직에 도달하지 못함.
- 수정 방향: APP_FAMILIES 체크를 packageName 1순위보다 앞으로 이동.

**버그 2. KB은행·네이버 등 → Play Store 화면 경유 (열기 버튼 눌러야 함)**
- 원인: `intent:#Intent;package=...;end` 스킴은 Android 12+ 패키지 가시성 제한으로 `Linking.canOpenURL()` 이 항상 false 반환. deeplink 실패 → fallback(Play Store 웹 URL) → 크롬에서 열림 → 사용자가 "열기" 클릭해야 함.
- 유튜브가 되는 이유: `vnd.youtube:` 커스텀 URI 스킴은 패키지 가시성 제한 대상이 아님.
- 수정 방향: `intent:` 스킴은 `canOpenURL` 건너뛰고 바로 `Linking.openURL()` 시도. 앱 미설치 시 catch → fallback.

**버그 3. 네이버 켜줘 → 크롬에서 네이버지도 열림**
- 원인: `APP_LINKS` 키 순서 + substring 매칭 버그. 테이블에서 `네이버지도`(deeplink: "nmap://") 가 `네이버`보다 먼저 선언됨. 매칭 로직 `k.includes(clean)`에서 `"네이버지도".includes("네이버") = true` → 네이버지도 키가 먼저 걸림. nmap 미설치 → fallback `https://map.naver.com` → 크롬 열림.
- 수정 방향: 완전 일치 → 입력이 키 포함 → 키가 입력 포함 순으로 매칭 우선순위 부여.

**버그 4. 지피티 켜줘 → 없다고 함**
- 원인: APP_LINKS에 ChatGPT 항목 없음. 별칭(지피티 → ChatGPT) 매핑 없음.
- 수정 방향: `챗GPT` 항목 추가 (package: `com.openai.chatgpt`) + 별칭 맵.

**버그 5. 갤러리·캘린더 못 열음**
- 원인: ① 갤러리: `intent:` 스킴 `canOpenURL` false (버그 2와 같은 원인). ② 캘린더: APP_LINKS에 항목 없음.
- 수정 방향: `intent:` 수정(버그 2 해결 시 함께 해결) + 캘린더 항목 추가.

### 다음 세션 결정사항

버그 패치보다 **PackageManager 방식으로 전면 교체** 결정 (기가지니가 쓰는 표준 Android 방법론).

| 현재 방식 | PackageManager 방식 |
|---|---|
| 하드코딩 테이블 (~60개) | 기기에 설치된 앱 전체를 런타임 조회 |
| 없는 앱은 "찾을 수 없어요" | 설치만 되어 있으면 자동 인식 |
| 테이블 관리 필요 | 테이블 불필요 |

- `react-native-installed-apps` 패키지 도입 예정
- 예상 작업 시간: 2~3시간
- 위 버그 5개가 자동으로 해결됨
