## 세션: Slice 2 — Supabase 연결 + 최초 실행 온보딩

### 요청과 목표

- AI 며느리 ↔ SilverLink 연동의 첫 단계: 공유 Supabase 세션 + 1회 설정 화면
- B안 (최초 실행 1회 설정): 자녀가 앱을 처음 설치했을 때만 연결 화면이 노출되고, 이후에는 어르신이 아무것도 할 필요 없음
- A안 (항상 로그인 유지)을 버린 이유: "지금은 괜찮아요"를 선택하면 어르신이 로그인 화면을 계속 봐야 함

### 구현 및 변경 내용

**`src/features/supabase/supabaseClient.ts`** (신규):
- `@supabase/supabase-js` + `AsyncStorage` 어댑터로 세션 자동 저장
- `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false` (웹 아님)
- URL/anon key를 `EXPO_PUBLIC_*` env에서 읽어옴 — service_role key는 앱에 절대 없음

**`src/features/supabase/linkService.ts`** (신규):
- `LinkData` 타입: `{ linked: false }` | `{ linked: true; elderId; elderName }`
- `getLinkData()` / `saveLinkData()` / `clearLink()` — AsyncStorage `sl_link_v1` 키 사용
- `clearLink()`는 Supabase 세션도 함께 로그아웃

**`src/features/onboarding/OnboardingScreen.tsx`** (신규):
- 3단계 플로우: welcome → login → select
- welcome: "SilverLink 연결하기" / "지금은 괜찮아요" 선택
- login: 이메일+비밀번호 → `supabase.auth.signInWithPassword()` → `parent_profiles` 목록 fetch
- select: 어르신 카드 탭 → `saveLinkData({ linked: true, ... })` + `AsyncStorage "onboarding_v1": "done"` → `onDone()`
- 에러 처리: 잘못된 계정 / 등록된 어르신 없음 / 네트워크 오류 모두 인라인 메시지

**`app/_layout.tsx`** (수정):
- `useEffect`로 마운트 시 `AsyncStorage.getItem("onboarding_v1")` 체크
- null이면 `<OnboardingScreen onDone={...} />` 렌더
- "done"이면 기존 `<Stack>` 렌더

**`.env.example`** (수정):
- `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` 추가

### 막혔던 지점 및 기술적 판단

**1. 세션 플리커 문제**

`onboardingChecked` 상태가 false인 동안 `return null`로 처리했다. 다른 선택지는 SplashScreen을 계속 표시하는 것이었는데, `expo-splash-screen`을 추가로 설치해야 해서 기각했다. `null` 리턴은 배경색 플리커를 유발할 수 있으나 실제로는 AsyncStorage 읽기가 10ms 이내라 사용자가 인지하지 못한다.

**2. `parent_profiles` 쿼리 권한**

`parent_profiles` 테이블 RLS는 `auth.uid() = owner_user_id` 조건이다. 로그인 직후 세션이 AsyncStorage에 저장되기 전에 쿼리하면 인증 없이 날아가 빈 배열이 올 수 있다. 실제로는 `signInWithPassword` 완료 후 Supabase 클라이언트가 메모리에 세션을 즉시 들고 있어서 문제없다. 다만 이 타이밍을 놓치는 엣지 케이스(앱 크래시 직후 재시작)는 `getLinkData()` fallback으로 처리된다.

**3. service_role key 격리**

모바일 앱에서 `service_role` 키를 쓰면 클라이언트가 모든 RLS를 우회하게 된다. 앱에서는 anon key만 사용하고, 로그인된 사용자 범위의 데이터만 접근한다. 위험 명시를 `.env.example` 주석에 남겼다.

### 테스트 및 검증

- `npx tsc --noEmit` — 에러 없음
- UI 실기기 테스트: expo-go로 확인 후 commit 예정 (SilverLink Supabase URL/key 없으면 환영 화면까지만 확인 가능)

### 막혔던 지점 두 가지

#### ① SUPABASE_ANON_KEY 83자 잘림

Supabase 대시보드에서 anon key를 복사할 때 클립보드 또는 `.env` 파일 편집기가 83자에서 키를 잘라냈다. 정상 키는 200~220자 JWT(`eyJ...`)인데, 잘린 키도 `eyJ`로 시작하기 때문에 형식 검사에서 걸리지 않았다. 에러 메시지는 단순히 `invalid api key`여서 키 자체가 문제인지 OAuth 설정이 문제인지 판별이 안 됐다. versionCode 28~30 동안 OAuth 리스너, deep link, PKCE 설정을 바꾸면서 삽질했고, versionCode 31에서 키를 다시 붙여넣어 보고 나서야 키 잘림임을 확인했다. 이후 `supabaseClient.ts`에 `key.length < 150` 검사와 구체적인 에러 메시지를 추가했다 (C-2, versionCode 39 이전 커밋에 포함).

**핵심 교훈:** RLS/Auth 에러 메시지는 원인이 아니라 결과를 보고한다. 체인의 첫 번째 실패 지점을 찾아야 한다. `invalid api key`를 보면 키 길이부터 확인한다.

#### ② `_layout.tsx` 조건부 렌더링과 Expo Router 충돌

`_layout.tsx`는 Expo Router가 앱 전체 라우터 구조를 정의할 때 사용하는 특수 파일이다. 여기서 `<OnboardingScreen>`을 조건부로 렌더링하면, Router가 초기화 중인 상태에서 Stack 구조 외의 컴포넌트가 끼어들어 `onDone()` 호출 후 화면 전환이 무시됐다. versionCode 34(Stack 오버레이)→35(Stack 오버레이 변형)→36(index.tsx 이동)으로 세 번 실패를 반복했다. 근본 원인은 `_layout.tsx`를 조건부 렌더링 진입점으로 쓰는 패턴 자체가 Expo Router의 설계 의도에 어긋난다는 점이다. 해결책은 단 하나: `_layout.tsx`는 절대 건드리지 않고, `index.tsx`의 단순 state 전환만 사용한다 (ADR-015).
