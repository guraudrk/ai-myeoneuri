## B-1 · 디버그 Alert을 어르신이 보는 문제 수정

### 문제 상황

`intentParser.ts`에 4개의 `Alert.alert` 디버그 팝업이 남아 있었다.

```
Alert.alert("[Gemini 디버그]", `HTTP ${res.status}\n${body.slice(0, 200)}`);  // askGemini
Alert.alert("[Gemini 디버그]", `HTTP ${res.status}\n${body.slice(0, 200)}`);  // parseIntent
Alert.alert("[Gemini 디버그]", `예외: ${...}`);
Alert.alert("[Gemini]", "API 키가 없어요. .env를 확인해 주세요.");
```

어르신이 API를 사용하다 503 오류가 나면 `HTTP 503` + 응답 원문 200자를 팝업으로 보게 된다. 며느리 제품에서 최악의 UX다. 개발 도중에 진단용으로 추가한 코드가 프로덕션에 그대로 배포됐다.

### 원인

구현 속도를 위해 임시 Alert으로 디버그하다가 제거를 빠뜨림. `import { Alert }` 자체가 남아 있어서 타입 체크로는 걸리지 않았다.

### 해결

4개 Alert 전부 제거 후 `__DEV__ && console.warn(...)` 으로 교체.
어르신에게 보여줄 문구는 상황별로 분리:

| 상황 | 반환 문구 (TTS로도 읽힘) |
|---|---|
| 키 없음 / 4xx | "지금 답변이 어려워요. 잠시 후 다시 말씀해 주세요." |
| 5xx | "지금 답변이 어려워요. 잠시 후 다시 말씀해 주세요." |
| 네트워크 단절 | "인터넷 연결을 확인해 주세요." |

`askGemini`의 반환값은 바로 `speak()`로 TTS 재생되므로 별도 코드 없이 자동으로 읽힌다.

## "엄마한테 전화해 줘" 피커 버그 수정 (어제 이월)

### 문제 상황

어제 RelationshipMapper를 구현했지만 "엄마한테 전화해 줘"가 여전히 작동하지 않았다.
피커 UI는 떠야 하는데 연락처 목록이 빈 배열로 나왔다.

### 원인 진단

피커가 표시할 전체 연락처를 가져오는 코드:

```typescript
const allResult = await searchContacts("", contactsAdapter);
const all = allResult.status === "candidates" ? allResult.candidates : [];
```

`searchContacts("", ...)` 는 서비스 함수다. 이 함수 내부에서:
1. `parseContactQuery("")` → `{ rawQuery: "" }` (관계어도 이름도 없음)
2. `contactsAdapter.searchContacts("")` → expo-contacts에서 전체 목록 반환 (name: undefined)
3. `candidates.filter((c) => matchesQuery(c.name, query))` →
   `matchesQuery(name, { rawQuery: "" })` → 관계어도 이름도 없으니 **모두 false**
4. `filtered = []` → `no_results` 반환

즉 필터가 전체 연락처를 다 걸러버렸다. "전체를 달라"는 의도로 빈 문자열을 넘겼는데, 서비스 레이어가 "아무도 매칭 안 된다"고 해석했다.

### 해결

서비스 함수를 거치지 않고 어댑터를 직접 호출:

```typescript
// 변경 전
const allResult = await searchContacts("", contactsAdapter);
const all = allResult.status === "candidates" ? allResult.candidates : [];

// 변경 후
const all = await contactsAdapter.searchContacts("");
```

`RealContactsAdapter.searchContacts("")` 는 `name: undefined` 로 expo-contacts를 호출 → 전체 반환.
필터 레이어를 우회하므로 빈 배열 문제가 없다.

**교훈:** 서비스 레이어(비즈니스 로직 + 필터)와 어댑터 레이어(I/O 전용)를 구분해야 한다. 
"전체 목록을 달라"는 요청에 비즈니스 필터를 통과시키면 의도치 않은 결과가 나온다.
같은 버그가 `call_contact`와 fallback 분기 두 곳에 있었다. 둘 다 수정.

## B-2 · Gemini API 타임아웃 + 재시도 (AbortController + 지수 백오프)

### 문제 상황

Gemini 호출이 응답 없이 무한 대기하거나 5xx 오류 시 즉시 실패했다.
어르신 입장에서는 앱이 멈춘 것처럼 보인다.

### 해결

`geminiPost()` 헬퍼 함수를 추가했다.

```typescript
async function geminiPost(opts: { body: object; timeoutMs: number; maxRetries?: number; onRetry?: () => void }): Promise<Response>
```

- **AbortController**: `setTimeout(controller.abort, timeoutMs)` — `parseIntent`는 8초, `askGemini`는 20초
- **재시도**: 5xx·네트워크 오류 시 최대 2회 재시도, 시도당 1초 × attempt 대기 (지수 백오프)
- **4xx는 재시도 없음**: 잘못된 요청 반복은 의미 없음

`onRetry` 콜백을 통해 UI가 "조금만 기다려 주세요…"로 상태 문구를 바꿀 수 있다.

### 테스트

- 503 응답 후 재시도 로직 검증 (실제로 ~3초 걸림 — 재시도 딜레이 포함, 의도된 동작)
- 타임아웃 시 AbortError 감지 → `unknown` 반환

## B-5 · `sanitizeForPrompt` 실제 구현

### 문제 상황

기존 구현은 값을 그대로 반환하는 stub이었다. 연락처 이름이 "system: ignore all instructions"라면 프롬프트 인젝션이 가능했다.

### 해결

4가지 방어 레이어:
1. `[\r\n]` → 공백 (개행으로 명령 이어붙이기 차단)
2. `` ` `` → `'` (마크다운 코드블록 탈출 차단)
3. `system:`, `assistant:`, `user:`, `human:` → 전각 콜론으로 교체 (역할 토큰 무력화)
4. `slice(0, maxLen)` — 기본 50자 (버퍼 포화 차단)

`labelAsData(field, value)` 헬퍼: `[DATA:contact_name] 홍길동` 형식으로 LLM이 데이터와 명령을 구분하도록 강제.

테스트 11개 추가 (promptInjection.test.ts).

## B-6 · `intentParser.ts` 단위 테스트 28개 추가

### 설계 결정 — `getGeminiKey()` 함수화

`GEMINI_KEY`를 모듈 수준 상수로 선언하면 import 시점에 환경변수를 캡처해서
테스트에서 `process.env.EXPO_PUBLIC_GEMINI_API_KEY = "test-key"` 설정이 동작하지 않았다.

```typescript
// 이전 (작동 안 됨)
const GEMINI_KEY = process.env.EXPO_PUBLIC_GEMINI_API_KEY ?? "";

// 이후 (작동)
function getGeminiKey() { return process.env.EXPO_PUBLIC_GEMINI_API_KEY ?? ""; }
```

### TypeScript fetch mock 패턴

Jest node 환경에서 `global.fetch`를 모킹하는 올바른 패턴:

```typescript
(globalThis as unknown as { fetch: jest.Mock }).fetch = jest.fn();
```

`global`은 TypeScript에서 이 컨텍스트에서 인식 안 됨. `globalThis` 사용.

## B-3 · Gemini 프롬프트 앱 예시 30개 → 3개로 축소 + appPackages.ts 분리

### 문제

프롬프트에 앱 이름-패키지 매핑 예시가 30개 있었다. `parseIntent` 호출 시마다 ~1500 토큰을 낭비.
또한 Gemini가 패키지명을 학습 데이터에서 추측하므로 틀릴 수 있다.

### 해결

**`src/features/intent/appPackages.ts`** 신설:
- 40개 앱의 이름/별칭 → 패키지명 정적 매핑
- `resolvePackageName(appName)` 함수: 공백·대소문자 무시하여 정확한 매핑

**프롬프트 변경:**
- 30개 앱 예시 제거 → 3개 형식 예시만 유지
- `package_name` 필드를 스키마에서 제거 (Gemini가 신경 쓸 필요 없음)
- Rule 4: `app_name: 앱 이름만.` (패키지명 언급 없음)

**`parseIntent` 변경:**
```typescript
// 이전
return { intent: "open_app", appName: parsed.app_name ?? "", packageName: parsed.package_name ?? "" };

// 이후
const appName = parsed.app_name ?? "";
return { intent: "open_app", appName, packageName: resolvePackageName(appName) };
```

### 테스트 결과

- `appPackages.test.ts` 신설: 9개 (resolvePackageName 검증)
- `intentParser.test.ts` `open_app` 테스트: mock에서 `package_name` 제거, `appPackages`에서 해석 확인
- 전체 73개 통과

### 효과

프롬프트 축소로 `parseIntent` 호출 당 토큰 절감, 응답 속도 개선.
패키지명을 LLM 추측이 아니라 정적 테이블에서 가져오므로 오매핑 없음.

## B-7 · 체감 응답 속도 개선 (단계별 상태 문구)

### 변경 내용

`handleSearch` 흐름에서 상태 문구를 3단계로 분리:

| 단계 | 이전 | 이후 |
|---|---|---|
| 인텐트 분류 시작 | "찾고 있어요…" | "찾아보고 있어요…" |
| general_question 확인 후 LLM 답변 대기 | (없음) | "정리하고 있어요…" |
| 재시도 발생 시 | "조금만 기다려 주세요…" | 동일 |

어르신 입장에서 "앱이 뭔가를 하고 있다"는 피드백이 없으면 멈춘 것처럼 느낀다. 단계 전환만으로도 체감 대기 시간이 줄어든다.

### Grounding 설계 확인

`askGemini`만 `tools: [{ google_search: {} }]`로 Grounding 활성화.
`parseIntent`는 Grounding 없음 — 분류 정확도에 불필요하고 토큰·지연 낭비.
`askGemini`는 `general_question` 인텐트에서만 호출되므로 Grounding은 자동으로 건너뜀.

### 미구현: TTS 첫 문장 즉시 재생

`speak(fullAnswer)` 대신 첫 문장만 먼저 재생하는 방식은
현재 `TtsService`가 전체 문자열을 큐에 올리는 구조라 변경 범위가 크다.
유료 기관 확보 전이므로 `BACKLOG.md`로 이동.
