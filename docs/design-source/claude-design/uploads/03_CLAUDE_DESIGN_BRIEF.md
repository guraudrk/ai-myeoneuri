# AI 며느리 — Claude Design 전달용 UI/UX 디자인 브리프


## 0. 프로젝트 확정 정정사항 — 다른 절보다 우선

아래 사항은 초기 브리프의 모호하거나 미흡한 부분을 정정한 최종 기준이다.

### 브랜드와 색상

- 화면 구조와 고령자 UX는 본 브리프의 원칙을 유지한다.
- 색상은 현재 SilverLink 앱과 같은 Blue·Navy 계열을 사용한다.
- Primary `#2E5BFF`, Pressed `#234AE0`, Primary Tint `#EEF2FF`, Primary Border `#DCE4FF`.
- Deep Navy `#12183F`, Support Navy `#1B2660`, Accent Blue `#5B8CFF`.
- Background `#F5F7FB`, Surface `#FFFFFF`, Border `#E7EBF3`.
- Text Primary `#101828`, Secondary `#475467`, Meta `#667085`.
- Success Text `#087443` / Tint `#ECFDF3`; Error Text `#B42318` / Tint `#FEF3F2`; Warning Text `#93370D` / Tint `#FFFAEB`.
- 기존 앱의 색상과 신뢰감만 계승하고, 복잡한 대시보드 밀도는 계승하지 않는다.
- Nocturne의 어두운 보라색 디자인 시스템은 제품 UI의 기준으로 사용하지 않는다.

### 권한 요청

- 최초 실행에서 마이크·연락처·전화·알림 권한을 연속 요청하지 않는다.
- 마이크는 사용자가 큰 마이크 버튼을 처음 눌렀을 때 요청한다.
- 연락처는 전화 명령이 확인된 뒤 연락처를 검색하기 직전에 요청한다.
- 알림은 첫 알림을 생성할 때 요청한다.
- 거부 시 흐름을 막지 말고 글자 입력, 홈, 설정 이동 등 대체 경로를 제공한다.

### 첫 MVP 전화 방식

- 첫 MVP는 Android `ACTION_DIAL`을 기본으로 한다.
- 앱은 확인 후 전화번호가 입력된 Android Dialer를 연다.
- 사용자가 시스템 통화 버튼을 직접 누른다.
- 따라서 첫 MVP의 핵심 흐름에는 `CALL_PHONE` 권한이 필요하지 않다.
- 화면과 TTS는 Dialer를 열었을 뿐인데 실제 통화가 시작됐다고 표현하면 안 된다.
- 완료 문구: `이지은 님의 전화 화면을 열었어요. 통화 버튼을 눌러 주세요.`
- 최종 확인 문구: `딸 이지은 님의 전화 화면을 지금 열까요?`
- 버튼: `전화 화면 열게요` / `열지 않을게요`.

### 뒤로 가기와 취소

- Dialer handoff 전까지 사용자는 언제든 뒤로 가거나 취소할 수 있다.
- 전화 화면을 여는 짧은 상태에서도 handoff 전이면 최종 확인 화면으로 돌아갈 수 있다.
- Dialer가 열린 뒤에는 Android 기본 뒤로 가기 동작을 따른다.
- 앱이 뒤로 가기를 장시간 차단하지 않는다.

### 오프라인과 부분 기능

- 연락처 검색과 `ACTION_DIAL` 자체는 로컬 기능으로 설계한다.
- Cloud STT 또는 AI 분석이 연결되지 않으면 글자 입력 대체 경로를 제시한다.
- `오프라인이라 아무것도 할 수 없다`는 식으로 전체 흐름을 차단하지 않는다.
- 권장 문구: `음성 기능은 지금 연결하기 어려워요. 글자로 입력하면 연락처를 찾을 수 있어요.`


## 1. 의뢰 목적

가칭 **AI 며느리** Android 앱의 MVP UI/UX를 설계해라.

이 앱은 스마트폰 사용이 어려운 고령자가 복잡한 메뉴를 배우지 않고도 자연어 음성으로 필요한 작업을 수행하도록 돕는 개인용 AI 에이전트다.

이번 작업의 중심은 화려한 브랜딩이 아니라 다음 세 가지다.

1. 고령자가 망설이지 않고 사용할 수 있는가
2. AI가 무엇을 하려는지 사용자가 이해할 수 있는가
3. 전화·문자처럼 실제 행동 전에 사용자가 명확히 확인할 수 있는가

제품명은 가칭이므로 이름이나 “며느리” 캐릭터를 시각 정체성에 과도하게 고정하지 마라.

---

## 2. 제품 한 문장

> 사용자가 자연스럽게 말하면 AI가 요청을 이해하고, 안전한 실행 계획을 보여주고, 사용자의 확인 후 스마트폰 작업을 수행하는 고령자용 음성 비서.

---

## 3. 주요 사용자

### Primary

- 작은 글씨를 읽기 어려운 고령자
- 앱 메뉴 구조를 기억하기 어려운 사용자
- 연락처 검색과 전화 걸기가 부담스러운 사용자
- 긴 설명이나 많은 선택지에서 피로를 느끼는 사용자
- 스마트폰을 잘못 누를까 두려운 사용자
- 전화에서 들은 할 일을 잊기 쉬운 사용자

### Secondary

- 자녀
- 보호자
- 가족 구성원

보호자는 주 사용자를 감시하는 사람이 아니라, 사용자가 요청했을 때 도움을 제공하는 보조자다.

## 4. MVP 핵심 사용자 흐름

### Flow A — 가족에게 전화

1. 홈 화면
2. 큰 마이크 버튼
3. 듣는 중
4. 인식된 문장 확인
5. 연락처 후보
6. 통화 대상 확인
7. 전화 연결 또는 Dialer
8. 완료·취소·오류 결과

대표 발화:

```text
딸한테 전화해 줘.
```

### Flow B — 생활 서비스 업체 검색 후 전화

1. 홈
2. 음성 명령
3. 위치 사용 설명
4. 업체 결과 최대 3개
5. 업체 상세 비교
6. 선택
7. 전화 확인
8. 결과

대표 발화:

```text
근처 보일러 수리공 찾아서 전화해 줘.
```

### Flow C — 통화 후 할 일 정리

1. 통화 종료 또는 테스트 이벤트
2. “해야 할 일을 정리할까요?”
3. 추출된 할 일 목록
4. 항목 하나씩 확인
5. 알림 시간 확인
6. 저장 완료

## 5. 설계할 화면

최소한 다음 화면과 상태를 설계한다.

### 5.1 시작·온보딩

- 앱이 무엇을 도와주는지 한 문장
- 음성, 연락처, 전화 기능의 이유
- 한 화면에 하나의 결정
- “나중에” 가능
- 보호자와 함께 설정하는 경로
- 개인정보를 과도하게 설명하지 않는 짧은 요약
- 자세히 보기

### 5.2 권한 설명

각 권한을 한꺼번에 요청하지 않는다.

필요 화면:

- 마이크 권한(첫 마이크 사용 시)
- 연락처 권한(연락처 검색 직전)
- ACTION_DIAL 전화 화면 열기 안내(별도 전화 권한 없음)
- 알림 권한(첫 알림 생성 시)
- 권한 거부 상태
- 설정에서 다시 허용하는 안내

권한 설명 예:

```text
“딸에게 전화해 줘”라고 말씀하셨을 때
연락처에서 딸을 찾기 위해 필요해요.
```

### 5.3 홈

필수 요소:

- “무엇을 도와드릴까요?”
- 화면 중심의 매우 큰 마이크 버튼
- 음성 대신 글자로 입력
- 최근 요청 최대 3개
- 보호자에게 도움 요청
- 항상 찾을 수 있는 설정
- 현재 상태가 명확한 음성 안내

메뉴와 기능을 많이 노출하지 마라.

### 5.4 듣는 중

- 크고 명확한 Listening 상태
- 중지 버튼
- 실시간 또는 부분 Transcript
- 주변 소음이 큰 경우 안내
- 시간이 길어지면 다시 말하기
- 녹음이 아니라 현재 명령을 듣는 중임을 명확히 표현

### 5.5 인식 결과 확인

예:

```text
“딸한테 전화해 줘”
```

행동:

- 맞아요
- 다시 말할게요

AI가 임의로 행동을 확정하기 전에 사용자가 문장을 확인할 수 있어야 한다.

### 5.6 연락처 후보

최대 3개.

각 카드:

- 이름
- 관계 또는 사용자가 이해할 수 있는 설명
- 사진은 선택적
- 전화번호는 전체 노출하지 않거나 일부 마스킹
- 매우 큰 선택 영역

후보가 없을 때:

- 다른 이름으로 찾기
- 보호자에게 도움 요청
- 연락처 앱 열기

### 5.7 최종 전화 확인

가장 중요한 안전 화면이다.

예:

```text
딸 이지은 님의 전화 화면을
지금 열까요?
```

버튼:

- 전화 화면 열게요
- 열지 않을게요

긍정 버튼과 취소 버튼을 색상만으로 구분하지 않는다.  
대상, 행동, 시점을 한 문장으로 읽어 준다.

### 5.8 전화 연결·결과

상태:

- 연결 준비
- Dialer 열림
- 전화 실행
- 사용자가 취소함
- 권한 없음
- 연락처를 찾지 못함
- 중복 요청 차단
- 알 수 없는 오류

오류 메시지는 기술 용어 대신 다음 행동을 제시한다.

### 5.9 업체 검색 결과

최대 3개.

카드 정보:

- 업체명
- 업종
- 현재 위치와의 대략적인 거리
- 영업 여부
- 전화 가능 여부
- 한 줄 추천 이유
- 정보 출처 또는 마지막 확인 시점

광고처럼 보이지 않게 한다.  
AI의 추천과 단순 검색 결과를 구분한다.

### 5.10 통화 후 할 일

각 항목은 Action Card로 만든다.

예:

```text
내일 오전 10시에 관리사무소에 전화하기
```

버튼:

- 알림 만들기
- 수정하기
- 필요 없어요

한 번에 많은 할 일을 확정하지 말고 항목별로 확인한다.

### 5.11 도움 요청

- 자녀 또는 보호자에게 도움 요청
- 무엇을 도와달라고 할지 짧은 요약
- 전송 전 확인
- 취소
- 연결된 보호자가 없을 때 설정 안내

### 5.12 설정

- 글자 크기
- 음성 속도
- 음성 볼륨 안내
- 보호자 연결
- 권한 상태
- 개인정보·기록
- 최근 실행 기록
- 로그아웃 또는 계정
- 긴급 중지 또는 접근성 기능 해제

설정도 깊은 계층을 피한다.

## 6. 필수 상태 설계

각 핵심 화면에서 다음 상태를 빠뜨리지 않는다.

- Idle
- Listening
- Processing
- Needs confirmation
- Executing
- Success
- Cancelled
- Permission denied
- No result
- Multiple matches
- Offline
- Provider unavailable
- Timeout
- Duplicate request blocked
- Partial completion
- Guardian approval needed

Loading만 보여주지 말고 현재 무엇을 하는지 문장으로 알려 준다.

예:

```text
연락처에서 “딸”을 찾고 있어요.
```

## 7. 접근성 기준

### Typography

- 본문 최소 20sp 수준
- 핵심 문장 24sp 이상 검토
- 한 줄 길이를 짧게
- 지나치게 가는 Font Weight 금지
- 숫자, 이름, 시간은 명확하게 강조
- 줄 간격 충분히 확보

### Touch

- 주요 버튼 최소 56dp
- 버튼 사이 충분한 간격
- 작은 Icon-only 버튼 금지
- 한 손 사용을 고려
- 주요 행동은 화면 하단에서 접근 가능

### Choice

- 한 화면 선택지 최대 3개
- 한 화면에 하나의 핵심 질문
- 긍정·부정 문구를 구체적으로 작성
- “확인/취소”보다 “전화 화면 열게요/열지 않을게요”처럼 실제 행동을 명시

### Contrast

- WCAG AA 이상을 목표
- 색상만으로 상태 구분 금지
- 밝은 야외에서도 읽을 수 있는 대비
- 다크모드는 후순위여도 구조는 고려

### Motion

- 필수 정보 전달을 Animation에 의존하지 않음
- 느리고 부드러운 상태 변화
- 빠르게 번쩍이거나 반복되는 Motion 금지
- Reduce Motion 대응

### Audio

- 화면과 음성에서 동일한 핵심 내용을 전달
- 음성만으로 중요한 선택을 강요하지 않음
- TTS 속도 조절
- 다시 듣기
- 음성이 잘못 들렸을 때 쉽게 수정

### Cognitive load

- 전문 용어 금지
- 긴 약관을 기본 화면에 노출하지 않음
- 무엇이 실행될지 미리 설명
- 완료 후 결과를 명확히 말함
- 뒤로 가기와 취소를 일관되게 배치

## 8. 시각 방향

원하는 인상:

- 현재 SilverLink Blue·Navy 계열의 브랜드 연속성
- 신뢰
- 침착함
- 생활 밀착
- 공공 서비스 수준의 안정감
- 병원 앱보다 개인적이고 친근함
- 유아용 앱처럼 보이지 않음
- 보호자 감시 앱처럼 보이지 않음
- 과도한 AI·로봇 이미지 사용 금지

피할 것:

- 차가운 사이버펑크
- 지나친 네온
- 복잡한 Dashboard
- 카드가 빽빽한 Layout
- 작은 회색 글씨
- AI 캐릭터가 사용자를 대신 지배하는 인상
- “며느리”를 특정 여성 캐릭터로 고정하는 표현
- 의료·응급 서비스로 오해될 수 있는 Red 중심 디자인

색상은 하나의 Primary, 하나의 Support, 명확한 Neutral과 상태 색상으로 제한한다.

색상 값을 확정할 때 대비 결과를 함께 제공한다.

## 9. Voice personality

말투:

- 존댓말
- 짧고 자연스러움
- 명령조가 아님
- 지나치게 아기처럼 말하지 않음
- 실패를 사용자 탓으로 돌리지 않음
- 한 문장에 하나의 행동

좋은 예:

```text
딸 이지은 님에게 지금 전화를 걸까요?
```

```text
연락처 사용이 허용되지 않았어요.
설정에서 허용하거나, 전화번호를 직접 입력할 수 있어요.
```

나쁜 예:

```text
요청하신 Intent Execution이 실패했습니다.
```

```text
사용자 오류로 연락처를 찾지 못했습니다.
```

## 10. 안전 확인 UX

전화, 문자, 내비게이션, 알림처럼 실제 행동이 발생하는 경우:

1. 대상
2. 행동
3. 시점
4. 취소 방법

## 12. 프로토타입 요구

다음 Prototype Flow를 연결한다.

### Prototype 1

```text
홈
→ 듣는 중
→ “딸한테 전화해 줘”
→ 연락처 후보
→ 최종 확인
→ Dialer/전화
→ 완료
```

### Prototype 2

```text
홈
→ 보일러 수리공 검색
→ 업체 3개
→ 업체 선택
→ 전화 확인
```

### Prototype 3

```text
통화 종료 알림
→ 할 일 정리
→ 할 일 카드
→ 알림 시간 확인
→ 저장 완료
```

Prototype에는 성공 흐름만 넣지 말고 다음 실패 흐름도 포함한다.

- 마이크 권한 거부
- 연락처 권한 거부
- 연락처 없음
- 이름이 같은 사람이 여러 명
- 오프라인
- 사용자가 취소
- 중복 요청
- 업체 검색 실패

## 13. 개발 전달 규칙

디자인 결과는 React Native/Expo 개발자가 해석할 수 있도록 제공한다.

필수:

- 화면별 목적
- 화면 진입 조건
- 화면 상태
- 사용자가 할 수 있는 Action
- 필수 데이터
- Error 상태
- 접근성 Label
- 읽기 순서
- Keyboard/Back 동작
- TTS로 읽을 문장
- Button 이름
- Component 재사용 관계
- Design Token 이름
- Android 기준 크기

디자인은 비즈니스 로직이나 API 구조를 새로 정의하지 않는다.

이미 확정된 시스템 흐름:

```text
입력
→ 의도 구조화
→ 안전 정책
→ 사용자 확인
→ 결정론적 실행기
→ Android 작업
→ 결과 검증
→ 결과 안내
```

UI는 이 흐름을 사용자에게 이해시키는 역할을 한다.
