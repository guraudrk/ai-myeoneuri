[GENERAL AI CODING AGENT OPERATING MANUAL — GUIDE]
부제: 범용 운영 매뉴얼의 개념, 적용 방법, 한계와 확장 방법


======================================================================
1. 이 문서는 무엇인가
======================================================================

범용 운영 매뉴얼은 프로젝트의 기능 요구사항이 아니다.

프로젝트 종류에 관계없이
AI 코딩 에이전트가 어떻게 일해야 하는지 정하는 방법론이다.

문서별 역할:

- Product Spec: 무엇을 만들 것인가
- Architecture: 어떤 구조로 만들 것인가
- Implementation Plan: 어떤 순서로 만들 것인가
- ADR: 무엇을 왜 결정했는가
- Operating Manual: Agent가 매 작업을 어떻게 수행할 것인가

따라서 Operating Manual은
AI 에이전트의 직무 규정과 작업 습관에 가깝다.


======================================================================
2. 어떤 프로젝트에 적용할 수 있는가
======================================================================

- 웹 서비스
- 모바일 앱
- REST / GraphQL API
- 데이터 파이프라인
- AI 애플리케이션
- 업무 자동화
- 사내 도구
- CLI
- 라이브러리
- 연구 코드
- 문서화 프로젝트
- 레거시 유지보수
- 테스트 및 배포 자동화

도메인별 세부 규칙은 별도 문서에 둔다.

범용 매뉴얼은 작업 방법만 정의한다.


======================================================================
3. 핵심 아이디어
======================================================================

핵심은 다음 식이다.

좋은 Agent 운영
=
명확한 목표
+ 반복 가능한 Workflow
+ 제한된 Tool
+ 검증 Evidence
+ 사용자 승인
+ 중지 조건
+ 기록

자율성만 높이면 좋은 Agent가 되지 않는다.

권한, 검증, 비용, 범위가 함께 통제돼야 한다.


======================================================================
4. 문서와 강제 장치의 차이
======================================================================

문서는 판단 기준이다.

- 무엇을 먼저 할지
- 언제 질문할지
- 어떤 테스트를 할지
- 어디에 기록할지

Hook, Test, CI, Permission은 강제 장치다.

예:

운영 문서:
“Secret을 커밋하지 마라.”

강제 장치:
- Secret scanner
- Pre-commit hook
- CI blocking rule

운영 문서:
“변경 후 Type-check를 실행하라.”

강제 장치:
- CI type-check job
- Merge protection

중요 규칙일수록 문서와 자동 강제를 함께 사용한다.


======================================================================
5. 왜 범용 문서와 프로젝트 문서를 분리하는가
======================================================================

범용 문서:

- 탐색
- 계획
- 실행
- 검증
- 기록
- 실패 대응
- 권한
- Context 관리

프로젝트 문서:

- 비즈니스 규칙
- 도메인 모델
- 기술 스택
- 현재 Phase
- 특수 보안 조건
- 사용자 경험

범용 문서를 프로젝트별로 복사한 뒤
프로젝트 특수 규칙을 덧붙일 수 있다.

하지만 도메인 세부 내용을 범용 문서에 계속 추가하면
다른 프로젝트에서 재사용하기 어려워진다.

======================================================================
7. 설치 방법
======================================================================

1. 범용 운영 매뉴얼을 다음으로 저장한다.

`docs/AGENT_OPERATING_MANUAL.md`

2. 범용 CLAUDE.md 템플릿을 프로젝트에 맞게 수정한다.

3. Product Spec, Plan, ADR을 준비한다.

4. 첫 실행 메시지 템플릿을 사용한다.

5. 반복 절차가 확인되면 Skill로 분리한다.

6. 반드시 강제할 검사는 Hook 또는 CI로 구현한다.


======================================================================
8. 매 작업에서 Agent가 달라지는 점
======================================================================

적용 전:

- 사용자가 파일을 하나씩 지정
- Agent가 즉시 코딩
- 테스트는 나중
- 범위가 쉽게 커짐
- 다음 세션이 상태를 잃음

적용 후:

- Agent가 관련 파일 탐색
- 목표와 완료 기준 정의
- 위험도 분류
- 작은 Slice 계획
- 구현 직후 검증
- 결정과 다음 일 기록
- 다음 행동 선택
- 위험하면 승인 대기


======================================================================
9. 자율성을 얼마나 줄 것인가
======================================================================

권장 단계:

LEVEL A — Guided
- 분석과 계획만 자동
- 모든 수정 승인

LEVEL B — Assisted
- 낮은 위험 수정과 테스트 자동
- 중간 이상 위험 승인

LEVEL C — Bounded Autonomous
- 승인된 범위 안에서 여러 Step 자동
- 예산·반복·Tool 제한
- 중요 Gate 승인

LEVEL D — Fully Autonomous
- 일반 프로젝트에서는 기본 권장하지 않음

초기에는 LEVEL B가 안전하다.


======================================================================
10. CLAUDE.md에는 무엇을 넣는가
======================================================================

넣을 것:

- Build/Test 명령
- 기술 스택
- 핵심 Convention
- Source of truth
- 금지 사항
- 운영 매뉴얼 경로
- 완료 전 필수 검증

넣지 않을 것:

- 긴 연구 자료
- 모든 Workflow 전문
- 긴 체크리스트
- 특정 기능의 상세 구현
- 일시적인 진행 상황

긴 절차는 Skill 또는 docs에 둔다.


======================================================================
11. Skill로 승격할 기준
======================================================================

다음 중 두 개 이상이면 Skill 후보:

- 같은 프롬프트를 세 번 이상 사용
- 여러 단계가 항상 같은 순서
- 특정 파일이나 Tool을 반복 사용
- 출력 형식이 고정
- 검증 방식이 고정
- 도메인별 지식이 필요
- 일반 Context에 항상 넣을 필요가 없음

Skill 예:

- implement-feature
- investigate-test-failure
- release-check
- update-provider-profile
- perform-security-review


======================================================================
12. Hook으로 강제할 기준
======================================================================

다음은 Hook 또는 CI가 적합하다.

- 반드시 매번 실행
- 놓치면 보안·품질 문제
- 판단보다 기계 검사가 정확
- 빠르고 결정론적
- 실패 시 차단해야 함

예:

- Secret pattern
- Formatter
- Protected file
- Dangerous shell command
- Type-check before completion
- Notification when input is needed


======================================================================
13. Subagent를 사용할 기준
======================================================================

Subagent가 유리한 경우:

- 긴 탐색 결과
- 긴 Test log
- 독립적인 보안 리뷰
- 대규모 문서 조사
- 메인 작업과 독립적인 검토
- Tool 권한을 제한해야 하는 부작업

Subagent가 불필요한 경우:

- 작은 코드 수정
- 파일 두세 개 탐색
- 메인 Agent가 이미 필요한 Context를 가짐
- 역할 분리가 오히려 통신 비용을 키움


======================================================================
14. 한계
======================================================================

운영 매뉴얼은 다음을 보장하지 않는다.

- 요구사항이 틀리지 않음
- Agent가 항상 올바른 판단
- 외부 API 안정성
- 모든 테스트 환경 사용 가능
- 무한 Context
- Production 안전성
- 법적 적합성

그래서 다음이 필요하다.

- Git
- Test
- CI
- Permission
- Human review
- Monitoring
- Backups
- Clear acceptance criteria


======================================================================
15. 가장 중요한 사용 원칙
======================================================================

사용자는 Agent에게 모든 구현 세부를 말할 필요는 없다.

대신 다음을 명확히 한다.

- 목표
- 범위
- 금지 사항
- 완료 기준
- 위험 허용 수준

Agent는 다음을 스스로 찾는다.

- 관련 파일
- 현재 구조
- 구현 순서
- 테스트
- 문서
- 작은 다음 행동

즉, 사용자는 방향과 승인에 집중하고
Agent는 운영 절차에 집중한다.
