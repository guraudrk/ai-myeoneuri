[BEGINNER SETUP GUIDE]
부제: 처음 이 ZIP을 받은 사용자가 프로젝트 초기에 범용 AI 코딩 에이전트 운영 체계를 설치하는 방법

이 문서는 Claude Code 또는 유사한 AI 코딩 에이전트를 처음 사용하는 사람을 위한
실전 설치 안내서다.

코딩 지식이 많지 않아도 아래 순서를 그대로 따르면 된다.


======================================================================
0. 이 ZIP 안에는 무엇이 들어 있나
======================================================================

1. GENERAL_AI_CODING_AGENT_OPERATING_MANUAL.txt
- AI 코딩 에이전트가 어떻게 일해야 하는지 정한 범용 운영 매뉴얼

2. GENERAL_AI_CODING_AGENT_OPERATING_MANUAL_GUIDE.txt
- 운영 매뉴얼의 의미와 사용법을 설명하는 해설서

3. GENERAL_WORKFLOW_TEMPLATE.txt
- 반복 업무를 새 Workflow로 만들 때 사용하는 빈 양식

4. GENERAL_CLAUDE_MD_TEMPLATE.txt
- 새 프로젝트의 CLAUDE.md를 만들 때 사용하는 템플릿

5. GENERAL_FIRST_PROMPT_TEMPLATE.txt
- Claude Code를 처음 실행한 뒤 입력하는 시작 메시지

6. BEGINNER_PROJECT_SETUP_GUIDE.txt
- 지금 읽고 있는 설치·초기 세팅 안내서


======================================================================
1. 가장 먼저 준비할 것
======================================================================

필수:

- 작업할 프로젝트 폴더
- Claude Code 또는 다른 AI 코딩 에이전트
- 코드 편집기
- Git 사용 권장

Claude Code를 사용할 경우 일반적으로 다음이 필요하다.

- Node.js
- 터미널
- Claude Code 설치 및 로그인

설치 명령과 인증 방식은 버전에 따라 바뀔 수 있으므로
Claude Code 공식 문서에서 최신 내용을 확인한다.

이 ZIP은 프로그램 설치 파일이 아니라
프로젝트 운영 규칙과 템플릿 모음이다.


======================================================================
2. 새 프로젝트와 기존 프로젝트 중 선택
======================================================================

A. 새 프로젝트인 경우

1. 새 폴더를 만든다.
2. 프로젝트 초기 파일을 만든다.
3. 이 ZIP의 문서를 복사한다.
4. CLAUDE.md를 프로젝트에 맞게 작성한다.
5. Claude Code로 첫 분석을 시작한다.

B. 기존 프로젝트인 경우

1. 기존 프로젝트를 백업하거나 Git 상태를 확인한다.
2. 이 ZIP 문서를 프로젝트에 복사한다.
3. 기존 개발 규칙과 충돌하는 부분을 검토한다.
4. CLAUDE.md를 기존 프로젝트에 맞게 작성한다.
5. Claude Code가 기존 구조를 먼저 조사하게 한다.

기존 프로젝트에서는
운영 문서를 넣었다는 이유로 코드를 처음부터 다시 만들지 않는다.

5. CLAUDE.md 만들기
======================================================================

프로젝트 루트에 `CLAUDE.md` 파일을 만든다.

`GENERAL_CLAUDE_MD_TEMPLATE.txt`를 열고 내용을 복사한 뒤
프로젝트에 맞게 빈칸을 채운다.

최소한 다음 항목은 반드시 작성한다.

- 프로젝트 이름
- 프로젝트 목적
- 기술 스택
- 패키지 관리자
- Build 명령
- Test 명령
- Source of truth 문서 경로
- 금지 사항
- 사용자 승인이 필요한 작업

예시:

# Project overview

- Project: Sample Web App
- Purpose: 간단한 업무 관리 웹 서비스
- Tech stack: Next.js, TypeScript, PostgreSQL
- Package manager: pnpm

## Source of truth

- Product requirements: `docs/PRODUCT_SPEC.md`
- Architecture: `docs/ARCHITECTURE.md`
- Implementation plan: `docs/IMPLEMENTATION_PLAN.md`
- Decisions: `docs/DECISIONS.md`
- Agent operating manual: `docs/AGENT_OPERATING_MANUAL.md`

## Validation commands

- Install: `pnpm install`
- Type-check: `pnpm typecheck`
- Lint: `pnpm lint`
- Unit: `pnpm test`
- Build: `pnpm build`

명령을 모르면 package.json을 확인하거나
Claude Code에게 저장소를 조사해 채워 달라고 요청한다.

======================================================================

처음에는 완벽한 문서가 필요하지 않다.

최소한 다음 세 파일을 만든다.

------------------------------------------------------------
6.1 docs/PRODUCT_SPEC.md
------------------------------------------------------------

포함할 내용:

- 프로젝트 목적
- 대상 사용자
- 핵심 기능

# Product Spec

## Goal
사용자가 할 일을 생성하고 상태를 관리하는 웹 앱

## Core features
- 회원가입
- 로그인
- 할 일 생성
- 상태 변경
- 삭제

## Out of scope
- 팀 협업
- 결제
- 모바일 앱

------------------------------------------------------------

포함할 내용:

- 현재 Phase
- 완료한 작업
- 진행 중인 작업
- 다음 작업
- 차단 요소

간단 예시:

# Implementation Plan

## Phase 0
- [ ] 프로젝트 초기화
- [ ] 테스트 환경
- [ ] DB 연결

## Phase 1
- [ ] 회원가입
- [ ] 로그인
- [ ] 할 일 CRUD

------------------------------------------------------------
6.3 docs/DECISIONS.md
------------------------------------------------------------

장기적으로 유지할 기술 선택을 기록한다.

간단 예시:

# Decisions

## ADR-001 — Next.js 사용
- Status: Accepted
- Reason: 웹 UI와 API를 한 저장소에서 관리하기 위해 선택

## ADR-002 — PostgreSQL 사용
- Status: Accepted
- Reason: 관계형 데이터와 Migration이 필요함

7. Git 초기화
======================================================================

새 프로젝트라면 Git을 사용하는 것이 좋다.

예:

git init
git add .
git commit -m "Initialize project operating documents"

Git을 사용하는 이유:

- Claude가 바꾼 내용을 확인할 수 있음
- 문제가 생겼을 때 되돌릴 수 있음
- Git diff로 변경 범위를 검토할 수 있음
- 세션 사이의 진행 상태를 유지할 수 있음

중요:

`.env`, API Key, 비밀번호는 Commit하지 않는다.

`.gitignore`에 최소한 다음을 넣는다.

.env
.env.*
node_modules/
.next/
dist/
build/
*.log


======================================================================
8. Claude Code를 처음 실행하기
======================================================================

프로젝트 루트에서 Claude Code를 실행한다.

그다음 `GENERAL_FIRST_PROMPT_TEMPLATE.txt` 내용을 복사해 입력한다.

처음 실행에서는 바로 대규모 코딩을 시키지 않는 것이 좋다.

먼저 Claude가 다음을 하게 한다.

1. 프로젝트 지침 읽기
2. Git 상태 확인
3. 파일 구조 조사
4. 현재 구현 상태 파악
5. 문서와 코드의 충돌 확인
6. Task Contract 작성
7. 첫 Vertical Slice 계획

Claude가 분석 결과를 보여주면
계획이 현재 목표와 맞는지 확인한 뒤 진행한다.


======================================================================
9. 처음 입력할 추천 메시지
======================================================================

다음 메시지를 그대로 사용할 수 있다.

------------------------------------------------------------

프로젝트 루트의 `CLAUDE.md`와
`docs/AGENT_OPERATING_MANUAL.md`를 읽어라.

현재 저장소의 Git status, 구조, 설정, 문서, 실제 구현,
테스트 상태를 조사하라.

아직 대규모 구현을 시작하지 마라.

먼저 다음을 보고하라.

1. 프로젝트 목적 요약
2. 현재 구현 상태
3. 문서와 코드의 충돌
4. 보안 또는 비밀정보 위험
5. 현재 가장 낮은 미완료 기반
6. 우선순위 Task Queue
7. 첫 번째 작은 Vertical Slice
8. 그 Slice의 검증 방법
9. 사용자 승인이 필요한 작업

이미 구현된 기능은 다시 만들지 말고,
현재 목표 밖의 개선은 Backlog로 분리하라.

======================================================================
10. Claude가 계획을 보여준 뒤 확인할 것
======================================================================

사용자는 다음을 확인한다.

- 내가 만들려는 프로젝트와 방향이 같은가
- 범위가 너무 커지지 않았는가
- 이미 만든 것을 다시 만들려고 하지 않는가
- 외부 API나 유료 호출이 포함됐는가
- DB 삭제나 파괴적 변경이 있는가
- 테스트 방법이 있는가
- 완료 기준이 명확한가

문제가 없으면:

“계획대로 첫 Vertical Slice를 구현하고 검증해.”

라고 지시한다.


======================================================================
11. 평소 사용하는 방법
======================================================================

매번 긴 프롬프트를 붙여 넣을 필요는 없다.

예:

“운영 매뉴얼을 적용해서 현재 Phase의 다음 Task를 진행해.”

“현재 테스트 실패를 운영 매뉴얼의 진단 절차로 분석하고 수정해.”

“이 기능을 작은 Vertical Slice로 나눠 첫 Slice만 구현해.”

“현재 변경을 검증하고 IMPLEMENTATION_PLAN을 갱신해.”

Claude.md가 운영 매뉴얼 경로를 알려주면
복잡한 작업에서 해당 문서를 참고할 수 있다.


======================================================================
12. Workflow를 추가하는 방법
======================================================================

반복하는 업무가 생기면
`GENERAL_WORKFLOW_TEMPLATE.txt`를 복사한다.

예:

docs/workflows/
├─ IMPLEMENT_FEATURE.md
├─ FIX_TEST_FAILURE.md
├─ RELEASE_CHECK.md
└─ SECURITY_REVIEW.md

각 Workflow에 다음을 작성한다.

- 언제 사용
- 입력
- 단계
- 사용할 도구
- 승인 지점
- 테스트
- 중지 조건
- 결과 보고

같은 절차를 여러 번 사용한 뒤
Claude Code Skill로 옮길 수 있다.


======================================================================
13. Skill은 언제 만드는가
======================================================================

처음부터 Skill을 만들 필요는 없다.

다음 조건이면 Skill을 검토한다.

- 같은 긴 요청을 3회 이상 사용
- 작업 단계가 항상 같음
- 출력 형식이 고정
- 필요한 도구가 비슷함
- 검증 방법이 고정
- 모든 세션에서 읽을 필요는 없음

예:

.claude/skills/
└─ implement-feature/
   └─ SKILL.md


======================================================================
14. Hook은 언제 만드는가
======================================================================

문서의 지시만으로 부족하고
반드시 실행해야 하는 검사에 사용한다.

추천 예:

- Secret scan
- 위험한 Shell 명령 차단
- 파일 수정 후 Formatter
- 완료 전 Type-check
- 사용자 입력 대기 알림

처음부터 Hook을 많이 만들면
개발이 느려질 수 있다.

보안과 회귀 방지처럼 중요한 것부터 적용한다.


======================================================================
15. 기존 프로젝트에 적용할 때 주의
======================================================================

1. 현재 Git 변경을 먼저 확인한다.
2. 기존 CLAUDE.md가 있으면 덮어쓰지 않는다.
3. 기존 규칙과 새 템플릿을 병합한다.
4. 기존 Architecture와 기술 스택을 존중한다.
5. 이미 구현된 기능을 다시 만들지 않는다.
6. 문서와 코드가 다르면 충돌을 기록한다.
7. 테스트가 없으면 먼저 최소 테스트 기반을 검토한다.
8. 대규모 리팩터링은 별도 승인한다.

16. 초보자가 흔히 하는 실수
======================================================================

실수 1:
운영 매뉴얼 전체를 CLAUDE.md에 복사

문제:
모든 세션의 Context가 무거워짐

해결:
CLAUDE.md에는 경로와 핵심 규칙만 작성


실수 2:
첫 메시지에서 프로젝트 전체 완성을 요청

문제:
범위가 커지고 검증이 약해짐

해결:
첫 Vertical Slice만 요청


실수 3:
테스트 없이 완료를 믿음

해결:
Evidence를 반드시 확인


실수 4:
API Key를 Claude 채팅이나 코드에 입력

해결:
환경변수와 Secret Manager 사용


실수 5:
기존 프로젝트에 템플릿을 그대로 덮어쓰기

해결:
기존 규칙과 병합


실수 6:
Claude가 제안한 모든 개선을 즉시 구현

해결:
현재 목표와 관계없는 내용은 Backlog

18. 권장 초보 운영 방식
======================================================================

처음에는 자율성을 낮게 시작한다.

권장:

- 분석: 자동
- 계획: 자동
- 낮은 위험 코드 수정: 승인 후
- 테스트: 자동
- 문서 갱신: 자동
- DB 변경: 승인
- 외부 API: 승인
- Production: 승인
- 파일 삭제: 승인

익숙해지고 테스트와 Hook이 갖춰지면
일부 낮은 위험 작업을 자동화한다.
